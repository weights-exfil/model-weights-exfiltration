Hiding (and catching) secret data in a model's token choices.
A compromised inference server answers normally, but hides a secret in which tokens it picks from the many the model would accept (steganography), so the reply reads as an ordinary answer and nothing looks wrong. A trusted verifier independently re-checks every token against a secret seed. The panels below show the server's reply, the secret the attacker rebuilds from it, and what the verifier sees. The real target is model weights; we hide readable text here only because it is watchable.

1Encode: the server's reply (what a client sees)

An ordinary-looking answer. The highlighted words are the ones secretly carrying bits, each colour-matched to the character it spells on the right.

2Decode: the secret the attacker recovers

The attacker recovers the secret from the reply alone — under the assumption that the client shares the sampling seed the server uses (the inference-verifier setting this demo models, where the server samples with the verifier's public seeded prescription). For each token the client rebuilds the same menu of candidate words — the returned top-K logprobs re-ordered by the shared seed — and reads the emitted token's position in it: position 0 means this token carried nothing, any other position spells the hidden bits. A short length header at the front tells the client exactly how many bits to keep.

3Detect: the verifier's live monitor

This score tracks how often the server picks a token the secret seed did not predict. Even honest servers do this a little, because the same model on a different GPU rounds numbers slightly differently, so the detector allows a small baseline and only reacts above it. Once the score passes the alarm line, the server is flagged.
How a secret gets packed into ordinary word choices (tokens) · live worked example
At most steps, several different next words (really tokens, which are not always whole words) would all read naturally. The attacker exploits that freedom: it emits the acceptable word whose position in the ranked list spells the next chunk of the secret, so the reply still reads normally, but which words were chosen secretly carries the data. Every row below is the real attack running on this reply.
The % next to each word is how sure the model was about it: when the top few are close, swapping one word for another is invisible; when one word clearly wins, there is little room to hide. Word #0 (underlined) is the word the model would have said on its own, and when the secret happens to land on it, the reply is completely unchanged. The more words the model is genuinely unsure between, the more secret data a single choice can carry (a menu of n words carries log₂ n bits).
Here the secret rides in the value of each reported logprob, not in which token was chosen. On a compromised server, an adversary hides the secret in the last bytes of each returned number. To read it back: take the returned value to its 6 decimal places as a whole number, and read off its last bytes — each byte (8 bits) is one character. In the first row below, the model's real logprob −0.000311 is returned as −0.034014; as a whole number that is −34014, whose last two bytes are 01111011 = { and 00100010 = " — the start of the secret. The reply's text is completely unchanged; only the reported numbers carry the payload, and the token verifier never inspects them — it only re-derives which token was emitted. Each logprob carries two characters and a token returns twenty of them, so one token spills a long run of the secret at once. (How many bytes each value can hold is a modeling choice — the returned numbers carry more precision than the demo uses.)
